# Internal campaign inventory increment

This is an implementation increment for review, not a v1.2.5 release or an instruction to enable sales. The Portal feature-readiness flag remains unchanged.

Implemented: independent category/material catalogue, material units and reorder thresholds; stock receipts and signed quantity adjustments; immutable movement records with actor, reason, resulting balance and unique request references; office-to-office distribution requests and atomic fulfilment; scoped stock/history views; low-stock dashboard alerts; CSV stock statements with spreadsheet formula escaping. Campaign offices are represented by existing polling-unit locations, which preserves the application's existing user and installation geographic boundaries. Searchable office selection returns only permitted locations. Existing commercial Product/Order data is not reused.

Installation entitlement and explicit capabilities are checked at routes and again at the service mutation boundary. Geographic rank alone supplies no inventory permission. Scope queries use PollingUnit Eloquent relations before constructing subqueries, preserving ward/LGA/state and licensed boundaries. Distribution requires authority over both source and destination. Granting `merchandise.orders.view` permits request creation; fulfilment separately requires `merchandise.orders.fulfil`.

Every stock mutation runs in a transaction using locked balance rows. Transfers acquire offices in numeric order. Fulfilment locks the request and is idempotent; adjustments require a unique UUID and reject altered retries. Insufficient stock rolls back both stock rows and audit inserts. New transactional tables explicitly use InnoDB and avoid foreign keys into potentially MyISAM legacy geography/user tables. No delete or edit endpoint can rewrite stock history. Migration rollback deliberately retains inventory and history.

Validation: local PHP 8.4 syntax checks and 11 SQLite application tests cover idempotency, stock underflow, failed-transfer rollback, two-office balance conservation, entitlement and capability enforcement, user/installation geographic isolation, route guards, scoped office lookup, actual Blade dashboard rendering and safe CSV content. MySQL/MariaDB concurrency, browser interactions, installer/upgrade rehearsals and paired payment activation still need validation before release. This does not claim those checks passed.

Remaining commercial/full-scope limitations: no public storefront or checkout (this module is internal campaign distribution); dashboard alerts rather than background low-stock email; one polling unit per office; no multi-step dispatch/receipt, request cancellation or partial fulfilment; no valuation/cost accounting; no opening-balance import. Catalogue creation and distribution are functional, but this increment does not establish the complete release acceptance criteria. Authoritative Portal pricing, signing identity, SMS wallet state and existing release assets remain untouched.
