## Phase A — issue 8

### Findings and causes

Issue 8 and its complete comment history were read. Portal's `app/Http/Controllers/API/DeploymentRegistrationController.php::verify` returned plain text and invalidated every subsequent use of the confirmation link. Core's `AuthenticatedSessionController::store` discarded the normal intended destination. Core registration message synchronization exposed a contact-verification boolean without an exact identity/domain response contract. Portal had a `domain_verified` field but no implementation establishing ownership for a secure browser-return destination.

Inspected Core registration and update controllers/services, registration/update Blade cards, login and access-level middleware, routes, `AutomaticUpdateFlow`, `UpdateDownloadAccess`, `UpdatePortalClient`, and Portal confirmation, automatic-update authorization and checkout/navigation code.

### Changes

- Portal provides a styled Blade confirmation page with an explicit continuation button. Its destination is a fixed path on the registered domain, never a request URL.
- A short-lived random server challenge verifies that the registered HTTPS host serves the same installation. The HMAC is domain/installation/challenge-bound, keyed with the existing deployment-token hash. It is not a login, update authorization, bearer credential, or browser-return parameter.
- Portal pins a checked public IPv4 DNS answer to the TLS connection, disables redirects and proxies, excludes private/reserved/multicast/shared address ranges, retains TLS verification, and bounds time and response size. Domains without an accessible public IPv4 HTTPS endpoint receive a safe manual-navigation fallback.
- Bearer-authenticated `GET /api/v2/campaign-manager/deployments/{uuid}/registration-status` returns exact installation ID, domain, contact email, and strict verification booleans. It rechecks domain binding.
- Core's protected `/superadmin/updates/contact-confirmed` refreshes that status and renders the existing updater review screen. Failure redirects to Official Updates with a safe message. A browser query never counts as proof.
- Normal login resumes this exact fixed intended destination for Super Admin. Other login destinations retain existing behavior. Non-Super Admin return attempts remain forbidden.
- Valid repeated links are idempotent. Expired/tampered links expose no destination. Pending or changed domains and unavailable services fail closed.
- Existing signed-release, entitlement, purchase and explicit installation-consent mechanisms remain in force. Confirmation creates no update intent and triggers no package download, staging, payment redirect/initiation, or installation.

Relevant paths: `app/Services/DeploymentRegistrationService.php`, `app/Http/Controllers/OfficialUpdateController.php`, `app/Http/Controllers/Auth/AuthenticatedSessionController.php`, `routes/web.php`, `routes/superAdmin.php`, and `resources/views/backend/shared/official-updates.blade.php`; Portal adds `app/Services/DeploymentDomainBinding.php` and `resources/views/deployment-support/contact-confirmed.blade.php` alongside its controller/routes.

### Migration and security impact

No Phase A migration. No tokens or signed confirmation secrets are inserted into the return link. The public challenge endpoint returns only an installation/domain-bound digest and has no session authority. A fresh server check is required after normal authentication. Old Core installations without the challenge endpoint remain compatible with Portal through the manual-navigation fallback.

### Tests and readiness

Added `tests/Feature/ContactConfirmationReturnTest.php` in both repositories, covering authenticated review, login continuation, every non-Super Admin level, strict identity/domain matching, outages, malformed booleans, challenge binding, repeat confirmation, expiration, and private DNS refusal. Updated Portal's prior replay expectation to the new idempotent behavior.

The paired confirmation suites have executed on GitHub runners. Portal full regression and production build checks pass after correcting a stateful HTTP-fake test. Core login continuation now uses the actual `login` request field. Final merge readiness is conditional on the exact current commit passing all gates in Phase D.

### Exact cross-repository dependency

Core requires Portal's new authenticated registration-status endpoint and exact response fields. Portal's return button requires Core's well-known challenge endpoint and protected fixed continuation route. The HMAC input is `campaign-manager-domain-v1`, installation UUID, lowercase registered domain, and 64-character hex challenge, separated by newlines; key is SHA-256 of the existing deployment bearer token. Both protocol halves must receive joint integration review before either PR merges. During a future authorized rollout, an old peer safely falls back; it must not be treated as a successful verified continuation.

Open acceptance item: root-host deployment is the supported return path. Subdirectory installations, IPv6-only hosts, and custom HTTPS ports require an explicitly reviewed extension rather than an arbitrary redirect parameter.

## Phase B — roles and capabilities

### Findings and causes

Spatie Permission v6 already exists. `CampaignPackagePermissionService` derived action rights from fixed role names. `CampaignPackageRoleService` bound named-role choices to access-level/package groups. `MembersController::updateMember` could replace roles and reset existing assignments when no role was submitted. Repeated member-table renderers showed action links using role-name lists. Member suspension was a GET mutation. Existing services also have independent module, assignment and geography guards that must remain in force.

The static inventory records 1,504 controller/action references in route source files, 1,414 mapped references and 497 distinct centrally mapped actions. Ninety account/authentication/installer references retain their dedicated guards. These are source-reference counts, not a successful Laravel runtime route listing. See `v1.2.0-route-capability-inventory.csv`. No active impersonation endpoint or application API routes were found; `routes/api.php` is empty. Unused Livewire imports have no corresponding components/routes.

### Changes

- `CampaignCapabilityService` centrally resolves independent actions for the actual modules, including members, election results, incidents, agents, community, announcements, geography, messaging, email, SMS, finance/settings, exports and updater controls.
- Spatie role and direct permission grants remain authoritative in managed mode. An explicit individual restriction takes precedence. Super Admin's operational permissions can also be restricted; authorization-management recovery remains reserved for the Super Admin account type.
- User and role opt-in markers keep customer/legacy assignments in compatibility mode until explicitly reviewed. Compatibility decisions report their source. Existing role-name mappings are confined to that compatibility bridge rather than the new managed-role model.
- `User::can`, Spatie permission checks, route middleware, and capability-aware navigation use the same decision service. A scoped service caches definitions/restrictions for the current request or queue lifecycle.
- A Super Admin interface creates/edits reusable roles, assigns independent actions, assigns existing users' roles without changing access level/geography, manages individual grants/restrictions, explains effective results, and configures defaults for future users.
- The legacy `group_name` enum is preserved. New reusable roles/definitions use its existing `user` value as a compatibility placeholder; the managed marker separates capabilities from that legacy grouping.
- Other administrators cannot select arbitrary roles during creation/import or replace roles during user editing. Creation applies a server-selected default. Omitted roles no longer reset customer assignments. Public member registration also uses the configured server default.
- Both legacy role-management controllers now explicitly require authenticated Super Admin regardless of route reuse. No permission grant can delegate `authorization.manage`.
- The route/action catalog independently checks endpoints. Lookup endpoints needed by create/update forms use explicitly listed alternatives, without implying view permission. Existing geographical, licensed-scope, account-type, assignment and record policies still apply.
- Election result creation and amendment check separate capabilities. Verification/dispute retains existing supervisory and geographic checks plus update capability.
- Member action rendering reuses the existing shared helper and reflects effective view/update/delete rights. Existing menus retain their routes, with 209 route links additionally filtered through the capability service.
- Suspension links now lead to a confirmation screen; mutation requires POST/CSRF. Existing URLs remain valid.
- Direct SMS workers recheck capability through their existing sending gate. Email workers check the sender's effective create capability before processing. Existing recipient/sending scope and module rules remain intact.

Main paths: `app/Services/CampaignCapabilityService.php`, `config/capability_routes.php`, `app/Http/Middleware/EnsureCampaignCapability.php`, `app/Http/Controllers/CampaignAuthorizationController.php`, `app/Models/User.php`, `CampaignPackagePermissionService.php`, `CampaignPackageRoleService.php`, `MembersController.php`, `MemberImportService.php`, result-permission service, worker gates, and existing navigation templates.

### Migration impact

`2026_10_25_000001_add_managed_campaign_capabilities.php` adds `capabilities_managed` flags to users/roles, `campaign_permission_restrictions`, and `campaign_default_roles`. It adds permission definitions idempotently through a dedicated seeder; it does not reset/reseed customer roles, replace pivots, remove legacy roles, or auto-adopt managed mode. No new foreign-key dependency is imposed on legacy table engines. The down operation intentionally retains authorization data.

### Tests, security and unresolved work

Added `ManagedCampaignCapabilitiesTest.php` and shared test fixtures: all 16 CRUD combinations across members/results/incidents, every access level's geographical boundary, read-only restrictions, Spatie/Gate agreement, direct-deny precedence, immutable management authority, role assignment without scope changes, defaults, mass-assignment/normal-edit escalation attempts, and additive migration replay. Existing scope/assignment/report/import/security suites remain required.

The capability, scope, import and authorization tests have executed on SQLite, MySQL 8 and MariaDB 10.11. The legacy role editor now explicitly adopts managed capabilities when canonical permissions are selected and preserves noncatalog customer definitions. Member creation/import uses server defaults; existing-member role controls are disabled and assignments use the Super Admin editor. All member/election action toolbars are centrally filtered. Pure unit fixtures preload empty permission relations. Regression testing exposed and repaired legacy member Notice Board visibility without granting announcement-management rights. Customer-specific default choices remain an explicit Super Admin decision; migration does not force managed mode.

No Portal dependency for Phase B. Review the final exact-commit CI results before sign-off.

## Phase C — incident evidence

### Findings and causes

Both administrative and member incident submissions wrote photographs directly to `Storage::disk('public')`, separately from incident persistence. Disk, MIME, byte size and original-name metadata were absent; failures could leave partial records. Administrative templates constructed `asset('storage/'.$file_path)` and assumed the public storage link/document-root mapping was valid. The general `FileStorageService` uses another local-upload/S3 convention, but these incident writers bypassed it. Thus successful incident uploads could fail to display when `/storage` was unavailable or pointed at a different location. This is a verified code-path defect; production files/symlinks were not inspected and missing bytes cannot be reconstructed by this change.

The administrative result-to-incident redirect discarded the selected election/polling unit and subsequently selected another ongoing/current election/profile location. No explicit polling-unit-result association was stored. Video display existed without a corresponding unified upload policy/metadata pipeline.

### Changes

- A single `IncidentEvidenceService` validates content, extension, count, dimensions and size; derives canonical location and result association from the approved polling-unit assignment; stores to a private evidence disk; and records metadata.
- Writes occur before incident/evidence insertion, with cleanup/compensation on failure, including nontransactional legacy-table failure cases. The UI receives a failure message rather than a false success.
- New uploads allow JPEG/PNG/WebP images and MP4/WebM video. Filename extensions are generated from server-detected MIME. SVG, executable extensions, mismatched content and excessive uploads are rejected. No transcoder is added.
- Authenticated evidence delivery checks capability and scope/assignment before resolving a database-selected file. Relative-path allowlists and realpath containment prevent traversal and symlink escape. MIME is rechecked before serving, with private/no-store, nosniff, safe disposition and range-capable local delivery.
- Historical public-disk records resolve against their original storage root without depending on a public symlink. Existing GIF/BMP photographs and QuickTime videos have safe legacy handling; unsupported video playback is a download. Unsafe/missing files produce a clear unavailable state.
- Shared responsive Blade forms/reports replace duplicated incident templates, with image/video previews, fallback/download links and error states. Reporter association now uses `agent_id`.
- The result's election and polling unit survive the optional incident redirect. New incident records link to the corresponding active result. Reporting no incident preserves the ordinary result submission outcome.
- Super Admin settings support images+videos, images-only, videos-only and no attachments, plus independent size/count limits. Defaults: three 2 MB images, one 10 MB video, four files total. Disabling new media never hides old evidence.
- A dry-run-first `campaign:incident-evidence:privatize` operator command copies and hashes historical public evidence before changing metadata. `--apply` copies only; later `--apply --remove-public` can remove hash-verified public originals once references are private. Relocation metadata supports that second pass. This command was **not run**.

Relevant paths: `app/Services/IncidentEvidenceService.php`, `app/Http/Controllers/IncidentEvidenceController.php`, both election submission controllers/services, evidence models, `config/filesystems.php`, `config/incident_evidence.php`, shared election Blade views, and `app/Console/Commands/PrivatizeIncidentEvidence.php`.

### Migration and security impact

`2026_10_25_000002_add_incident_evidence_metadata.php` adds nullable disk/MIME/name/byte-size/legacy-public-path metadata to both evidence tables, nullable incident-to-result association, and the system settings policy field. Existing evidence/result/incident rows are retained; historical associations are not guessed/backfilled. Down intentionally retains data. New evidence uses local private storage under Laravel's preserved storage tree; it does not silently move evidence into a differently configured S3 account.

Old public copies remain publicly reachable until a future authorized relocation/removal is completed. An application controller alone cannot revoke direct static URLs. This operational privacy step is an explicit pre-deployment review item, not something performed on production during this assignment. Existing backups/storage mappings must be verified first.

### Tests, unresolved items and readiness

Added `IncidentEvidenceTest.php`: private uploads/retrieval and result association; video; policy changes and legacy access; invalid MIME/extensions/SVG/count/size; unauthorized and out-of-scope access; missing/traversal paths; settings authority; write failure; dry-run/copy/remove relocation; no-incident result submission; and independent result creation/amendment.

Upload/retrieval, policy, scope, historical-path, missing-file and compensation tests execute on SQLite, MySQL and MariaDB. The video regression uses an actual small H.264 MP4, with real file MIME detection rather than a synthetic upload MIME. The incident remarks column is widened additively to nullable text to honor the existing 5,000-character validation. Codec support remains browser-dependent; secure download remains available. Production historical files and real-browser playback have not been inspected by this report. No Portal dependency.
